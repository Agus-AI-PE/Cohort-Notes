#### ==*Common Pattern*==
- why pattern matter?
	- karena llm itu cuma bisa 1 fokus task 
	- tanpa patterns -> one giant promps akan sulit di-debug, sulit di-test, sering berubah behavior ketika tasknya grows

- dengan pattern
	- bisa di-split menjadi kecil-kecil

##### ==Prompt Routing==
![Pastedimage20260701154107084|652](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260701154107084.png)
- beda task (req user) beda intruksi
- mengklasifikasikan req user, lalu mengirim req ke prompt yang tepat (semestinya) / INTENT
- routing -> mencegah 1 generic asisten meng-handle setiap task/kasus
- metode ini menambah latensi
	- karena ada pre-prosesnya (mengklasifikasikan dulu)
	- ngakalinnya pake model yang lebih rendah (cheap and fast) -> untuk extractedIntent
- ![Pastedimage20260623011015165|628](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260623011015165.png)

> NOTE: perlu untuk di-log -> prompt yang dimasukin ke dalam proses extractedIntent
	>- dengan begitu kita akan tau kenapa output-nya halu
	>- ganti llm yang lebih bagus, frontier llm tidak serta merta menjadi better outputnya
	>- most of the time -> datang dari konteks req (apakah system prompt nya/intructions/ data yang dimasukin)

- ==context injection kalo di-inject negative (misal, overwrite system prompt dengan intruksi bahaya) dari user prompt bagaimana?==
	- dg konsep input-output guardrail di luar llm sebagai interseptor
	- ```
	  [ User Input ] ─> [ INPUT GUARDRAIL (Cek teks bahaya) ] ─> [ LLM (System Prompt) ] ─> [ OUTPUT GUARDRAIL (Cek kebocoran data) ] ─> [ User ] 
	  ```
		- input guardrail -> dijalankan sebelum req sampai pada main agent
			- ekstraksi dulu (extractedIntent) or klasifikasi apakah req mengandung prompt jailbreak ato tidak -> kalo iya, maka tolak
		- output -> dijalakan ketika llm sudah generate output dan siap di-serve ke user
			- cek untuk eksplisit kebocoran data -> bisa dg another llm call
	- guardrail -> intensinya untuk make sure risk action di-block
	- guardrail -> deterministic (pasti); pake kalkulator untuk 1+1 hasilnya 2; regex; static string matching; if else  -> di dashboar kita bisa tentukan role A tidak bisa melihat data X-Z dan beberapa orang tertentu bisa melihat data A-Z
	- guardrail -> non-deterministic (probabilistik); pake chatGPT buat nulis puisi, tekan button "send promp" 2x hasilnya berubah-ubah -> SYSTEM_PROPMT

#####  ==Structured Extraction & Research extraction pipeline==
- satu set messy information menjadi satu informasi yang terstruktur; case-nya-> dapat data dari internet
- program butuh data (schema) bukan paragraf
- gunakan ini ketika next stepnya code/database/workflow automation
- research extraction -> generate search queries, gunakan ketika task perlu current public information dari berbagai sumber (web, search engine, etc)
- why? research extraction pipeline
	- one search query sering to shallow. dengan multiple targeted search bisa mengimprove coverage-nya

- example case: 
	- mendapatkan data dari internet -> search tool: tavily
	- ![Pastedimage20260623212159857|621](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260623212159857.png)
	-   ![Pastedimage20260623212820197|616](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260623212820197.png)
	- input user itu hanya menerima string, kalau bukan string ubah dengan stringify

- as human gak tau apa atau search dengan query apa -> maka butuh llm untuk men-generate query tsb untuk kita -> yg selanjutnya query tsb dipake untuk input di search engine (dalam case ini pake search tool: `tavilyClient.search(query)`) untuk gather informasi 
- ![Pastedimage20260623215124712|665](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260623215124712.png)

- namun karena bentuknya array -> lakukan search dengan beberapa proses bersamaan -> caranya bisa pake `Promise.all`  
- lalu map sebuah tavily call
- nah data yg didapet dilooping secara sequensial satu-satu biar setiap topicnya diekstrak satu-satu. jangan giant prompt one shot.

#####  ==Evaluator and optimizer==
![Pastedimage20260701155015014|685](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260701155015014.png)
- semacam guardrail tapi
	- kalo guardrail intensinya -> nge-block action yang punya risiko
- kalo evaluator -> clasifyer untuk make sure apakah output ke user sudah tepat sesuai kriteria evaluation schema atau belum
- pondasi untuk loop engineering
- workflow-nya:
```markdown
  draft -> evaluation -> if(!evaluation.data.passed) revision step
```

#####  ==Parallel fan-out and fan-in==
- bermacam kacamata/pov independent specialists untuk mereview problem yang sama, lalu combine their views

![Pastedimage20260701212321637](https://raw.githubusercontent.com/Agus-AI-PE/notes-media/main/Pastedimage20260701212321637.png)

	- tanya ke ChatGPT: founder punya ide  -> sering kali founder butuh masukan (apakah ide ini bisa dimonet, bisa dijual, bisa didevelopkah) -> kalo tanya ke seperti chatGPT, kalo prompt-nya tidak spesifik -> result-nya akan dikasih dari 1 view saja.
	- bikin tools dg workflow/pipeline parallerl fan-out and fan-in: yang punya multiple views. seperti dari bisnis people, engineering people, product people.
